# Level metadata mine volume and travel time study

## Goal
- Study feasibility and algorithms for adding normalized mine volume and route-based travel time to level metadata.
- Pay special attention to locked-door/key routing and partial failure reporting.

## Plan
- [x] Inspect current native level metadata scan flow and available level data.
- [x] Identify geometry volume calculation options and D1 level 1 baseline source.
- [x] Identify path graph, locked door, key, hostage, reactor, and exit detection inputs.
- [x] Propose routing algorithm, failure modes, output schema, and validation approach.

## Findings

### Mine volume
- Feasible as a deterministic pass over loaded segment geometry.
- Use each segment center as an internal point, split each quad side into two triangles, and sum the six side pyramids. This gives a stable convex-polyhedron estimate using the same segment vertex data the game already loads.
- Convert fixed-point coordinates to double before cross products and volume accumulation to avoid overflow and make normalized comparisons stable.
- Normalize against a hardcoded D1 level 1 baseline generated by this exact algorithm, with a fixture/test that recomputes D1 L1 and fails if the algorithm or baseline drifts.

### Travel time
- Feasible as an approximate "completion route estimate", not an optimal route solver.
- Build a weighted segment graph from segment centers. Endpoint distances should include object/start/exit position to segment center, then center-to-center path cost through the mine.
- Treat normal connected sides, ordinary doors, blastable walls, and passable illusions as traversable. Treat closed walls and unsupported locked/trigger-only doors as blockers. Key doors become conditional edges requiring blue/red/gold key bits.
- Collect route targets from existing loaded globals through adapter callbacks: player start, hostage objects, key powerups including contained keys, control center/reactor, and exit trigger/external exit sides.
- Use a greedy route:
  1. Start at player start.
  2. Visit every hostage by nearest next reachable hostage.
  3. Visit reactor/control center.
  4. Visit nearest exit.
  5. When a selected path first reaches a locked key door without the key, route from before that door to the required key, add the return trip to the door, acquire the key, then retry the original target.
- Exact hostage ordering would be a constrained traveling-salesman problem. Greedy nearest-hostage routing is the recommended first implementation because the result is a readable metadata estimate and should be stable across large custom levels.
- Convert distance to time with no-afterburner cruise speed. D2 defines MAX_VELOCITY as 50 units/sec; use 50.0 DXX units/sec unless a later pass deliberately models ship physics.

### Failure reporting
- Add status fields rather than crashing or hiding partial data:
  - ok: all hostages, reactor, and exit reached.
  - partial: some route distance was computed, but completion failed.
  - failed: no useful route could be started.
- Useful failure reasons:
  - non-contiguous geometry / target unreachable
  - missing reactor
  - missing exit
  - required key missing
  - required key unreachable before door
  - locked door without key requirement
  - trigger-opened door routing unsupported
- Still report partial distance/time and target progress when status is partial.
