## Side colors

`gameio/loadgeometry.cpp:396` reads RGB regardless of the registration flag.
Registration sets `gameStates.render.bColored` if any component is strictly
between zero and one. `LoadSideLightsCompiled` registers side colors;
`LoadVertLightsCompiled` registers vertex colors. In the native pilot inventory,
440 vertex records and 49 side records meet that predicate. Those numbers are
different from the chromatic counts (392 vertices and 36 sides): fractional
gray also registers

`CColorData::lights` is an independently allocated array, separate from `sides`,
`ambient` and `textures` (`include/descent.h:1496`, `main/gamedata.cpp:1922`).
A full source-reference audit finds the serialized side-color array written by
the loader, with no rendering consumer. Its registration side effect remains
relevant: `GatherStaticLights` rebuilds ambient in legacy mode only when
ambient color is enabled and `bColored` is false. The pilot's vertex records
already set it true, so side registration does not change that decision here.
This is specific to the pinned source and pilot, not a general claim that side
colors can be discarded in every XL version or level

## Texture emitters

Texture colors have real consumers: `lighting/dynlight.cpp:961,970` uses them
when constructing geometry lights, and `effects/glare.cpp:325` uses them for
corona RGB when ambient color is enabled. `IsLight` reads a separate brightness
table (`lighting/light.cpp:875`), not the color record's index or HAM lighting
value. Default brightness comes from `descent2.lgt`, then a level-specific
`.lgt` may override it (`gameio/piggy.cpp:564`, `gameio/loadgame.cpp:1010`,
`gameio/loadgamedata.cpp:665`). Embedded level RGB supersedes the earlier
default/external texture RGB load

## Reference-run limitation and next implementation step

The opt-in runtime now exposes `xl_preview_texture_emitter`, which selects the
live base/overlay texture using the reference strengths, applies native wall
and light-subtraction state, checks bitmap-name exclusions, and returns authored
RGB and the reference base/strip intensity scale. The sparse brightness header's
94 entries reconstruct all 3640 original bytes with the SHA-256 above. This is
the exact pilot's default table, not general support for mission `.lgt` overrides

The native lifecycle test finds 112 eligible emitters, including all 24
chromatic candidates. For every eligible face it checks original RGB, native
`subtract_light`/`add_light` suppression and recovery, removal of both luminous
textures, and applicable wall-disable/cloaking exclusions. Stock transitions
must return no emitter. The controlled probes reload the original level before
later tests because subtracting UVL light can clamp its values. The required
test marker explicitly says rendering is unverified. At that checkpoint no
rendering consumer or occlusion test had been added. Both desktop targets build and the lifecycle
test passes (1.90 seconds; `temp/xl-emitter-build.log`)

The subsequent renderer uses these live queries, a procedural radial gradient,
and a native center visibility query before drawing with depth writes disabled.
The lifecycle test now verifies visibility from all 112 local segment centers
and 148 solid-wall negative controls. The Android controlled-view test passes
15 steps and observes actual draw submissions. This does not yet prove halo
pixels, partial/object occlusion or the classic-depth path. The inspected lava
view is saturated enough that a separate framebuffer comparison is still needed

The subsequent owned-framebuffer probe exposed a real renderer defect. With
the normal `GL_CW` front face and back-face culling, the counterclockwise halo
fan submitted successfully but produced zero pixels. Run
`ad8f37814a494e46b402288c4c1d3561` failed step 12/16 with zero GL errors;
both the unobstructed and half-blocked passes had zero lit pixels. Evidence:
`temp/xl-corona-culling-negative-test.log`,
`temp/xl-corona-culling-negative-pixels.json`, and
`temp/xl-corona-culling-negative-result.json`. The earlier probe with culling
disabled passed and was insufficient. Draw counters alone cannot establish
visible output. The renderer now constructs its fan clockwise; the regression
probe retains normal culling instead of disabling it to conceal this defect

The corrected build passes the unchanged 16-step test, run
`6d396ff0f87d461787764516f44160e6` (19539 ms). Visible pixels: 854 on each
half; nearer left-half depth: 0 left / 854 right; fully blocked: 0 / 0.
Every lit pixel matches the authored orange ratio within quantization tolerance;
all GL errors are zero and depth-write state is restored. Results are in
`temp/xl-corona-culling-fixed-pixels.json` and
`temp/xl-corona-culling-fixed-result.json`; the full test/build logs use the
same prefix. This controlled FBO proves GPU color and depth behavior, not the
population of the real scene's depth buffer or classic-depth/object occlusion

Classic-depth follow-up: the active pilot now selects the existing depth-buffered
mine/object path, retaining the stored classic-depth preference for stock levels.
The Android test passes 22 steps while switching that preference on and off:
run `78b8caa470dd49c2a50b8f5d87411401`, 75 draws checked with classic requested,
zero draws with depth testing disabled. Native lifecycle tests verify selection
and unchanged preference across pilot/stock transitions. See
`temp/xl-depth-policy-android-state.json` and the corresponding test/result files.
This closes the known disabled-depth pipeline defect, not the remaining need
to verify actual scene geometry and object occlusion in the framebuffer

Actual-scene wall depth is now verified at the controlled segment-40 view.
An explicit hook before normal halos uses `GL_ANY_SAMPLES_PASSED` queries
against the existing scene buffer, with both color and depth writes disabled.
The authored halo produces samples with depth on/off; the same halo moved
behind its opaque wall produces samples only with depth off. All queries
complete without GL errors. Run `37e68e95b5374cacbc596fc174de4f83` passes
24/24 steps (26796 ms); see `temp/xl-scene-depth-report.json` and corresponding
test/result files. The behind-wall control is deliberately synthetic positioning
of the halo, while the occluding depth comes from actual level rendering.
This is not yet an object-silhouette test or exhaustive scene coverage

The object-pass follow-up passes too: run `5ce89588721f4c4997deb399596be57f`,
28/28 steps in 24634 ms. A small synthetic halo behind existing robot anchor
89 is visible before the normal object pass and fully hidden afterward, with
the same framebuffer and no simulation step between queries. It becomes visible
again with depth disabled. GL errors are zero. The probe disables color/depth
writes, changes no robot or world state, and restores queried GL state. This
separates object-pass depth from wall depth, which was already present during
the positive pre-object control. Evidence: `temp/xl-object-depth-report.json`
and corresponding test/result files. It establishes this object-occlusion path,
not an authored robot emitter, all silhouettes, or reference-image equivalence

The existing ar12 profile has `render.nLightingMethod=0`, `render.color.nLevel=2`
and **`render.coronas.bUse=0`**. Its scratch game also lacks the optional data
HOG and corona/glare images. The old log's `found hog file 'd2x-xl.hog'` is not
evidence that it loaded: `CHogFile::Use` logs that text whenever the supplied
name is nonempty, even when `Setup` fails (`io/hogfile.cpp:198-214`)

Therefore the starting-room screenshot and baked-vertex arithmetic tests cannot
qualify texture-emitter rendering. Re-run reference observations with explicit
resources and corona settings, keeping the old baseline intact. Then implement
the pilot's authored emitter colors with light-off/destruction/flicker handling
and normal occlusion. Do not approximate this by tinting the entire textured
face or adding the emitter RGB again to already baked ambient lighting. Exact
halo image matching is unnecessary, but ignoring authored emitter behavior is
not a completed extension port
